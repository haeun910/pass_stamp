# 자체 리뷰 기록

## 1차 리뷰 (v1 MVP 기준, 2026-11-06)

v1은 4단계 화면과 에이전트 4개가 동작하는 최소 형태였어요. 실제 취업 준비 흐름에 대입해 보면서 부족한 점을 정리했어요.

### 사용 흐름
| # | 문제 | 왜 문제인가 | 조치 |
|---|---|---|---|
| F1 | 지원 건마다 서류가 하나뿐 | 실제로는 한 회사에 이력서, 자소서, 포트폴리오를 같이 내요. 자소서를 쓰면 이력서가 덮어써져요. | 지원 건별 서류 여러 개, 서류마다 종류와 문항 |
| F2 | 평가 결과를 반영해 고치는 흐름이 없음 | "평가 → 수정 → 재평가"가 이 서비스의 핵심 가치인데 사용자가 직접 복사해서 고쳐야 해요. | "피드백 반영해 수정본 만들기", 추가 요청으로 고쳐쓰기 |
| F3 | 수정하면 이전 내용이 사라짐 | 다시 쓰기를 누르면 마음에 들던 초안이 날아가요. | 서류 버전 기록과 되돌리기 |
| F4 | 자소서 문항·글자 수를 구조적으로 못 넣음 | 한국 자소서는 문항별 글자 수 제한이 핵심인데 자유 입력뿐이었어요. | 문항 + 글자 수 입력, 문항별 글자 수(공백 포함/제외) 자동 계산과 초과 표시 |
| F5 | 내 경험이 텍스트 칸 하나 | 무엇을 적어야 할지 막막하고, 기존 이력서가 있어도 옮겨 적어야 해요. | 섹션별 "내 프로필" 페이지, 기존 이력서 PDF/텍스트 불러오기(자동 정리) |
| F6 | 면접 기록이 한 번뿐이고 점수 추이가 없음 | 연습은 여러 번 하는데 이전 면접과 비교할 수 없어요. | 면접 세션 여러 개 저장, 점수 기록 |
| F7 | 예상 질문을 미리 볼 수 없음 | 실전 면접 전에 질문 리스트와 답변 방향을 보는 게 가장 흔한 준비 방식이에요. | 예상 질문 + 답변 가이드 생성 |
| F8 | 면접이 텍스트 채팅뿐, 시간 압박 없음 | 실제 면접은 말로 하고 시간이 정해져 있어요. | 음성 답변(브라우저 음성 인식), 질문 읽어주기, 답변 타이머, 질문 수/난이도/압박 면접 설정 |
| F9 | 지원 현황을 한눈에 볼 수 없음 | 여러 회사에 동시에 지원하니 마감일과 진행 상태가 필요해요. | 지원 건 대시보드(상태, 마감 D-day, 진행도, 최근 점수, 메모) |
| F10 | 결과물을 꺼낼 방법이 없음 | 결국 서류는 복사하거나 파일로 제출해야 해요. | 복사, .md/.txt 다운로드, 인쇄/PDF 저장 화면 |
| F11 | 채용공고 URL을 못 넣음 | 공고를 매번 복사해 붙이기 번거로워요. | 공고 URL을 넣으면 리서치 에이전트가 직접 읽음 (web_fetch) |

### 에이전트 품질
| # | 문제 | 조치 |
|---|---|---|
| A1 | 리서치 중 수십 초 동안 화면에 아무 변화가 없음 | 스트림에 진행 상태 이벤트 추가 ("'토스 인재상' 검색 중", "공고 페이지 읽는 중", "생각하는 중") |
| A2 | 생성을 중간에 멈출 수 없음 | 중지 버튼, 서버까지 요청 취소 전달 |
| A3 | 평가 점수를 기계적으로 읽을 수 없음 | 점수 형식을 고정하고 파싱해서 대시보드에 표시 |
| A4 | 면접관이 질문 수와 난이도를 모름 | 면접 설정을 프롬프트에 전달, 진행 중 질문 번호 표시 |
| A5 | 서류 작성 시 지어낸 경험이 섞일 위험 | 프로필에 없는 사실은 [ ]로 표시하라는 규칙 강화, 평가관도 근거 없는 주장을 지적 |

### 운영과 안정성
| # | 문제 | 조치 |
|---|---|---|
| O1 | API 키가 없을 때 오류가 결과 칸에 섞여 나옴 | 시작 시 상태 점검, 상단 안내 배너 |
| O2 | 로그인이 없는데 배포하면 누구나 API 키를 쓸 수 있음 | 선택형 접근 코드(APP_ACCESS_CODE), IP별 요청 제한, 입력 길이 제한 |
| O3 | 데이터가 브라우저에만 있어 날아갈 수 있음 | JSON 백업 내보내기/가져오기 |
| O4 | API 키 없이 화면을 테스트할 수 없음 | 모의 응답 모드(AGENT_MOCK=1) |
| O5 | 한 페이지에 모든 상태가 있어 뒤로 가기, 링크 공유가 안 됨 | 경로 분리 (/profile, /apply/[id]?tab=…, /settings) |

### 1차 리뷰 반영 결과
위 표의 F1~F11, A1~A5, O1~O5를 모두 v2에 반영했어요. 자세한 기능은 README에 정리했어요.

## 2차 리뷰 (v2를 실제로 돌려보며, 2026-11-06)

모의 응답 모드(AGENT_MOCK=1)로 프로덕션 빌드를 띄우고, 브라우저 자동화로 전체 흐름(프로필 가져오기 → 새 지원 → 리서치 → 자소서 작성 → 고쳐쓰기 → 평가 → 피드백 반영 수정 → 모의 면접 → 피드백 → 예상 질문 → 개요 → 홈 → 인쇄 → 새로고침 후 유지 → 모바일)을 14단계로 돌렸어요. 12단계 통과, 2단계 실패였고, 화면 캡처를 하나씩 보면서 아래 문제를 찾았어요.

| # | 발견한 문제 | 영향 | 조치 |
|---|---|---|---|
| R1 | 자소서 소제목(**굵은 줄**)과 본문이 한 문단으로 붙어 보임 | 에이전트가 줄을 나눠 써도 마크다운이 한 줄 바꿈을 무시해서, 제출용 글처럼 안 보여요. | 한 줄 바꿈을 그대로 살리도록 렌더링 변경 (remark-breaks) |
| R2 | 문항별 글자 수 표에서 문항 이름이 "1. 지원 …"으로 잘림 | 어느 문항인지 알아보기 어려워요. | 문항별 카드형으로 바꾸고 채움 막대와 남은 글자 수 표시 |
| R3 | 고쳐쓴 뒤 무엇이 바뀌었는지 볼 수 없음 | 피드백 반영 결과를 믿고 쓰려면 비교가 필요해요. | 직전 버전과 단어 단위 비교 보기 추가 (추가는 초록, 삭제는 빨강 취소선) |
| R4 | 서류를 고쳐도 서류 탭 배지에 예전 평가 점수가 그대로 보임 | 수정본도 72점인 것처럼 오해할 수 있어요. | 평가 후 수정된 서류는 점수 옆에 "수정 전" 표시 |
| R5 | 모바일에서 생성 결과가 설정 카드 아래에 있어 한참 스크롤해야 보임 | 쓰기를 눌러도 아무 일도 없는 것처럼 느껴져요. | 좁은 화면에서는 결과 카드를 위로, 생성 시작 시 결과 위치로 스크롤 |
| R6 | 평가의 "꼭 고칠 부분"이 번호 목록과 인용문이 분리돼 "1." 혼자 남음 | 마크다운 번호 목록 안에 인용문을 넣기 어려운 형식이었어요. | 평가 프롬프트 형식을 "**1. 제목**" 줄 + 인용 + 수정안으로 변경 |
| R7 | 이력서 가져오기 후 붙여넣은 원문이 입력칸에 그대로 남음 | 다시 누르면 중복으로 더해져요. | 반영 후 입력칸 비우기 |
| R8 | 모의 응답이 면접 두 번째 턴에서 첫 인사를 반복 (테스트 실패 원인) | 실제 API에는 영향 없고 모의 응답 판별 로직 문제였어요. | 대화 길이로 판별하도록 수정 |
| R9 | "고쳐쓰기" 입력칸을 테스트에서 찾지 못함 (테스트 실패 원인) | 입력칸에 이름과 안내 문구가 없어 화면 낭독기에서도 구분이 어려워요. | 입력칸에 placeholder와 aria-label 추가 |
| R10 | 평가 화면에서 점수 변화가 2회 이상일 때만 보임 | 첫 평가 뒤 어떤 점수인지 서류 목록에서만 확인 가능해요. | 유지 (2회부터 추이가 의미 있음). 대신 서류 목록에 최근 점수 표시는 그대로 |

### 실제 API로는 아직 확인하지 못한 부분
- 이 환경에는 Claude API 키가 없어서 실제 모델 응답(웹 검색 리서치, PDF 가져오기, 구조화 출력)은 타입 검사와 빌드까지만 확인했어요. 키를 넣고 처음 돌릴 때 리서치 1회, 자소서 작성 1회, 평가 1회, 면접 3턴, 이력서 PDF 가져오기 1회를 확인해 보는 걸 권해요.
- 음성 인식은 크롬/엣지에서만 동작해요. 자동화 브라우저에는 마이크가 없어 수동 확인이 필요해요.

### 2차 리뷰 반영 결과
R1~R9를 고친 뒤 같은 14단계 자동 테스트를 다시 돌려 모두 통과했어요 (`scripts/e2e-mock.cjs`, 모의 응답 모드). 브라우저 콘솔 오류는 테스트 환경에서 외부 글꼴(Pretendard CDN)을 못 불러온 것뿐이었어요. 모바일(390px) 화면에서 가로 스크롤이 생기지 않는 것도 확인했어요.

다시 돌리는 법:
```bash
npm run build && AGENT_MOCK=1 npx next start -p 3000 &
node scripts/e2e-mock.cjs ./e2e-out
```

## 3차: 유료 서비스용 화면 개편 (합격도장)

이름을 "합격도장"으로 바꾸고, 돈을 받는 서비스에 필요한 랜딩·요금·약관 화면을 더했어요. 앱 화면은 "흰 종이 위 남색 잉크, 채점은 빨간 펜" 하나의 방향으로 맞췄어요.

| # | 발견한 점 | 고친 내용 |
|---|---|---|
| U1 | 첫 화면이 바로 앱이라 처음 온 사람이 무엇을 하는 서비스인지, 얼마인지 알 수 없음 | `/`는 랜딩, `/pricing` 요금, `/terms`·`/privacy` 약관, 앱은 `/app`으로 분리 |
| U2 | 점수가 숫자 배지뿐이라 결과의 무게감이 없음 | 점수를 둥근 도장(`ScoreStamp`)으로 찍음. 80점 이상 초록 "합격권", 미만 빨강 "보완 필요" |
| U3 | 서류 결과가 일반 카드와 같아 "제출할 글"로 보이지 않음 | 서류 결과를 종이처럼(함렛 글꼴, 넓은 행간), 채점의 "꼭 고칠 부분"은 빨간 물결 밑줄 |
| U4 | "평가"와 "채점"이 섞여 버튼 이름이 화면마다 다름 | 탭, 단계, 버튼을 모두 "채점"으로 통일 ("회사 기준 채점", "채점받기") |
| U5 | 완료 표시가 글자(✓)라 글꼴에 따라 네모 상자로 보임 | 아이콘으로 교체 |
| U6 | 비교 화면의 추가·삭제 색이 브랜드와 따로 놂 | 삭제는 빨간 펜 취소선, 추가는 초록 형광 |
| U7 | 글꼴을 외부 CDN에서 불러와 막힌 환경에서 깨짐 | Pretendard, 함렛을 npm 패키지로 자체 호스팅 |
| U8 | 사업자 정보·요금이 여러 파일에 흩어질 위험 | `src/lib/site.ts` 한 곳에서 관리 |

자동 테스트는 랜딩·요금 화면과 모바일 가로 넘침 검사를 더해 15단계 모두 통과했어요. 콘솔 오류는 없었어요.

### 출시 전에 남은 것
- 결제(토스페이먼츠)와 로그인(카카오), 요금제별 사용량 제한. 지금 요금 화면 버튼은 모두 무료 앱으로 연결돼요.
- 약관·개인정보처리방침은 초안이라 전문가 검토가 필요하고, `site.ts`의 사업자 정보 자리표시를 채워야 해요.
- 상표 "합격도장" 등록 여부 확인 (KIPRIS).

## 4차: 개발 파트너 지침 기준 코드 점검 (2026-11-06)

하은 님의 "AI 개발 파트너 기본 지침"(정확성, 안정성, 보안, 검증 가능성)을 기준으로 서버와 화면 코드를 다시 읽었어요. 아래 표의 "확인 방법"이 비어 있지 않은 항목만 고쳤다고 적었어요.

### 고친 문제

| # | 심각도 | 문제 | 고친 내용 | 확인 방법 |
|---|---|---|---|---|
| C1 | 높음 | 생성이 **오류로 중간에 끊기면** 반쯤 쓴 글이 서류 본문과 새 버전으로 저장됨 (리서치, 예상 질문, 면접 질문도 같음) | 오류면 시작 전 내용으로 되돌리고, 사용자가 직접 멈춘 경우만 남김. 버전 이름에 "(중지됨)" 표시 | 자동 테스트: 오류 응답을 흉내 내 원문이 그대로인지 확인 |
| C2 | 높음 | 저장 데이터나 백업 파일에 항목 하나만 빠져도 화면이 깨지고, 깨진 데이터가 저장돼 **앱이 계속 열리지 않을 수 있음** | 불러올 때와 백업을 읽을 때 빠진 항목을 기본값으로 채움 (`normalizeData`) | 자동 테스트: 일부러 깨진 데이터를 넣고 홈과 서류 화면이 열리는지 확인 |
| C3 | 높음 | 이력서 PDF를 10MB까지 받는데, Vercel 함수 요청 한도는 4.5MB라 **배포하면 3MB가 넘는 PDF는 항상 실패** | 3MB로 낮추고 안내 문구 변경 (화면, 서버, README) | 코드 확인 (실제 Vercel 배포로는 확인 못 함) |
| C4 | 중간 | 저장을 0.4초 모아서 하는데 스트리밍 중에는 계속 미뤄져 **생성이 끝날 때까지 저장이 안 됨**. 탭을 바로 닫으면 마지막 입력이 사라질 수 있음 | 최대 2초 간격으로 저장, 탭을 닫거나 숨길 때 즉시 저장 | 수동 스크립트: 입력 직후 새로고침해도 남는지 확인 |
| C5 | 중간 | 면접 중 질문을 받다가 목록으로 나갔다 오면 답변 칸이 잠긴 채 **다시 진행할 방법이 없음** | "다음 질문 받기" 버튼 표시, 첫 질문 실패 시 "다시 시도" | 수동 스크립트로 두 경우 모두 확인 |

### 확인하지 못한 것과 남은 위험

- **실제 Claude API로는 한 번도 돌려보지 못했어요** (이 환경에 키가 없음). 리서치의 웹 검색, 이력서 PDF 읽기, 생각 토큰을 포함한 출력 한도, 긴 리서치의 이어 요청은 코드와 문서로만 확인했어요.
- 음성 인식은 마이크가 없어 확인하지 못했어요. 다크 모드 화면은 이번에 다시 캡처하지 않았어요.
- **로그인과 결제가 없는 상태로 공개 배포하면** 주소를 아는 누구나 운영자의 API 비용을 쓸 수 있어요. IP당 요청 제한은 서버 인스턴스마다 따로 세는 메모리 방식이라 남용을 막지 못해요. 결제 전까지는 `APP_ACCESS_CODE`를 꼭 켜 두세요.
- 요금 화면은 아직 구매할 수 없는 요금제와, 앱에 적용되지 않은 한도(체험 1곳, 프로 전용 모드 등)를 보여줘요. 이대로 공개하면 표시와 실제가 달라요. 결제를 붙이기 전에는 "출시 예정"으로 표시하거나 숨기는 걸 권해요.
- 약관과 개인정보처리방침은 여전히 초안이고, 사업자 정보는 비어 있어요.

## 5차: 유료 서비스 기준 보안·개인정보·저장 점검 (2026-11-08)

실제 API를 연결하기 전에, 돈을 받는 서비스라는 기준으로 보안, 개인정보 처리, 저장을 다시 봤어요. 결론부터 적으면 **지금 구조(로그인 없음, 브라우저 저장)로는 "유료 상용 서비스"가 아니라 "접근 코드를 아는 사람만 쓰는 비공개 베타"까지가 안전한 범위**예요. 아래 표의 수정으로 베타에 필요한 수준은 맞췄고, 유료 공개에 필요한 나머지는 "남은 결정"에 적었어요.

### 확인한 것 중 문제없던 것

- 마크다운 렌더링: HTML을 그대로 넣지 않고(`rehype-raw` 없음), 링크는 `http(s)`만 허용되고 새 창은 `noreferrer`. 모델 출력으로 스크립트를 넣을 수 없어요.
- 비밀값: `.env*`는 git에서 제외, 브라우저로 가는 `NEXT_PUBLIC_` 변수 없음, API 키는 서버에서만 사용.
- 요청 위조(CSRF): 쿠키를 쓰지 않고 JSON POST에 커스텀 헤더를 쓰므로 다른 사이트에서 요청을 보낼 수 없어요.
- 서버는 사용자 내용을 로그에 남기지 않아요. 오류 원문만 서버 로그에 남아요.
- 회사 리서치에는 프로필을 보내지 않아요.

### 남은 결정 (유료 공개 전에 필요)

1. **API 비용 노출.** 로그인이 없으면 접근 코드가 유일한 벽이고, 코드는 한 사람이 공유하면 끝이에요. 요청 제한은 서버 인스턴스마다 따로 세는 메모리 방식이라 Vercel에서는 거의 동작하지 않아요. 유료 공개 전에 로그인과 사용자별 사용량 한도(서버 저장)가 필요해요. 그 전까지는 **초대한 사람에게만 접근 코드를 주는 비공개 베타**로 운영하는 게 안전해요.
2. **저장 위치.** 브라우저 저장은 서버 유출 위험이 없다는 장점이 있지만, 돈을 낸 사용자의 서류가 브라우저 정리 한 번에 사라지는 건 환불 분쟁으로 이어져요. 로그인과 함께 서버 저장(Supabase)으로 옮기고, 그때 저장 데이터 암호화와 삭제 요청 처리를 설계해야 해요.
3. **Anthropic 데이터 보관.** 기본 설정에서는 API 입출력이 남용 감시 목적으로 일정 기간 보관돼요. 처리방침에 정확한 기간을 적으려면 Anthropic 콘솔의 현재 정책을 확인해야 하고, 민감한 서류를 다루는 서비스라면 보관하지 않는 계약(zero data retention)을 검토할 가치가 있어요.
4. **법률 검토.** 약관·처리방침은 초안이에요. 특히 국외 이전 고지 방식과 환불 기준은 전문가 확인이 필요해요.
5. **CSP 강화.** 지금은 iframe 차단만 해요. 스크립트 출처까지 제한하는 CSP는 Next의 인라인 스크립트 때문에 nonce 설정이 필요해 이번에는 넣지 않았어요.

### 이번에도 확인하지 못한 것

- 실제 Claude API 호출 (S4의 프롬프트 효과, 생각 토큰 포함 출력 한도, PDF 가져오기)
- 마이크가 있는 브라우저에서의 음성 인식
- 저장 공간이 실제로 가득 찼을 때의 동작

### 왜 "예시 지원 건" 방식인가

미리보기를 별도 화면(이미지나 읽기 전용 페이지)으로 만들 수도 있었지만, 그러면 실제 화면과 어긋나기 쉽고 유지비가 두 배예요. 실제 데이터 구조로 만든 예시를 그대로 앱에 넣으면 **사용자가 보는 화면이 곧 미리보기**이고, 버튼을 눌러 보며 흐름을 익힐 수 있어요. 대신 예시가 실제 지원 건과 섞이지 않도록 "예시" 표시, 이전 서류 목록에서 제외, 삭제 안내를 넣었어요. 예시 내용은 전부 가상이고 실제 회사·인물과 무관해요.

## 7차: 메인 색 교체 (2026-11-08)

하은 피드백: "지금은 너무 AI 스타일". 확인해 보니 3차 개편 때 디자인 스킬을 불렀지만, 남색 브랜드 + 파란 기 도는 회색(Tailwind slate) + 흰 둥근 카드 조합은 스킬이 스스로 "흔한 기본값"이라고 경고하는 쪽에 가까웠어요. 이번에는 색만 바꿨어요 (요청 범위).

- **방법:** 서비스 소재(원고지, 채점 펜, 인주 도장)에서 후보를 뽑고, OKLCH로 밝기 단계를 맞춘 세 팔레트(원고지 초록, 자주, 먹)를 실제 화면에 입혀 지금 남색과 나란히 캡처해 비교했어요. 처음엔 900 단계를 너무 어둡게 잡아 네 안이 거의 똑같아 보여서, 버튼·제목 색이 색으로 읽히도록 밝기와 채도를 올리고 회색까지 같이 바꿔 다시 비교했어요.
- **적용:** 원고지 초록. 인장의 빨강과 보색이라 도장이 먼저 보이고, 파란색이 대부분인 국내 채용 서비스와 구분돼요. 합격 초록(pass)과 같은 계열이라 "초록 = 통과, 빨강 = 고칠 곳" 규칙이 화면 전체에서 일관돼요.
- **같이 고친 것:** 하드코딩된 남색 그림자 4곳을 브랜드에서 파생한 변수(`--shadow-ink`)로, 공유 이미지·브라우저 테마 색, 다크 모드에서 "예시" 표시 글자가 배경에 묻히던 문제(6차에서 생긴 것), 공유 이미지 제목의 쉼표만 다음 줄로 넘어가던 줄바꿈.
- **검증:** 린트·타입·빌드 0 오류, 자동 테스트 23단계 라이트·다크 모두 통과, 라이트·다크·모바일 캡처 확인.
- **남은 것 (의견):** 색을 바꿔도 "똑같은 둥근 카드가 반복되는 화면 구성"은 그대로라 AI 툴 같은 인상이 일부 남아요. 레이아웃 손질은 요청하시면 별도로 해요.


## 8차: 비공개 베타 점검 (2026-11-08, 실제 API 호출 전)

`APP_ACCESS_CODE`를 켠 production 빌드(`next build` + `next start`)로 확인했어요.

- **확인됨:** 코드 없음·틀린 코드는 `/api/agent`, `/api/import` 모두 401. 보안 헤더(HSTS, X-Frame-Options DENY, nosniff, CSP frame-ancestors, 마이크 같은 출처만) 정상. 주요 화면 200, 없는 주소 404.
- **고친 것 (보안 버그):** 틀린 코드 20회로 IP가 잠긴 뒤에도 **맞는 코드는 통과**했어요. 그래서 잠긴 뒤에도 "틀림=429, 맞음=200"으로 갈려 추측을 계속할 수 있었어요. `/api/health`의 `codeOk`도 잠금과 무관하게 맞고 틀림을 알려 줘서, 시간당 120회까지 추측 창구가 됐어요.
  - `checkCode()` 한 곳에서 잠금·확인·횟수 세기를 하고, 잠긴 IP는 맞는 코드도 429. health도 같은 함수를 써요.
  - 코드를 아직 안 넣은 요청(화면 첫 로딩의 상태 확인)은 추측이 아니라서 세지 않아요. 안 그러면 새로고침만으로 잠겨요.
  - 잠기면 화면 상단과 설정에 "1시간 잠김"을 따로 보여 줘요 (전에는 맞는 코드를 넣어도 "접근 코드 필요"만 떠서 원인을 알 수 없었을 것).
  - 자동 테스트도 "잠긴 IP는 맞는 코드도 429, 다른 IP는 통과"로 바꿨어요.
- **검증:** 타입·린트·빌드 0 오류, 자동 테스트 23단계 통과(콘솔 오류는 일부러 여는 404 페이지 1건), production 서버에서 curl로 잠금 동작 확인.
- **남은 것:** 잠금은 서버 인스턴스 메모리 기준이라 인스턴스가 여러 개면 느슨해요(5차와 같음). 그래서 접근 코드는 추측하기 어려운 긴 값(16자 이상 무작위)으로 정해 주세요. API 키가 없을 때 뜨는 배너는 운영자용 문구(`.env.local`)라 베타 사용자에게는 어색할 수 있어요.
- **아직 안 한 것:** 실제 Claude API 호출(키가 이 작업 환경에 아직 없음), README 원가표 실측 갱신.


## 9차: 실제 Claude API로 품질·원가 측정 (2026-11-08)

8차까지는 모의 응답으로만 확인했어요. 이번에는 실제 API 키로 production 빌드(`next build` + `next start`)를 띄우고, 이력서 가져오기와 6개 에이전트를 실제 화면에서 한 번씩 돌렸어요. 앱 코드는 바꾸지 않았어요.

### 측정 방법

- **시나리오:** 가상의 지원자 김지원(프론트엔드, 인턴 1회, 프로젝트 2개, 주민등록번호 한 줄 포함) → 토스 프론트엔드 개발자(공고 URL 없음) → 자기소개서 기본 2문항(700자) → 채점 → 피드백 반영 수정 → 예상 질문 → 모의 면접(기본 설정, 본 질문 7개).
- **방법:** Playwright로 실제 화면을 눌러 진행(서류·채점·수정·예상 질문·면접). 원가는 서버 로그 `[usage]` 한 줄씩. 면접 답변은 미리 써 둔 답변 10개 중 질문 단어로 고른 것이라, 꼬리질문과 맞지 않는 답이 일부러 섞여 있어요.
- **환경 제약:** 이 클라우드 작업 환경(네트워크 "제한됨")에서 보낸 요청은 Claude API가 `web_fetch_20260209` 도구를 400으로 거부했어요(`Requests sent from a sandbox with restricted network access are not allowed to use tool web_fetch`). `web_search`는 됐어요. 그래서 회사 리서치만 앱과 같은 프롬프트·참고 자료·설정(effort medium, 검색 8회 한도, pause_turn 이어 받기)으로 부르되 web_fetch만 뺀 스크립트로 쟀고, 그 결과를 지원 건에 넣은 뒤 나머지를 화면으로 진행했어요. Vercel 같은 일반 서버에는 해당하지 않는 제약이에요.
- **가격 확인:** `src/lib/server/usage.ts`의 단가(입력 $4, 출력 $20, 5분 캐시 쓰기 $5, 캐시 읽기 $0.20, 웹 검색 $0.01/회)는 현재 Opus 5.5 정가와 같아요. web_fetch는 별도 요금이 없고 읽은 내용만 토큰으로 잡혀요.

### 품질: 발견한 문제 (고치지 않음, 결정 필요)

1. **수정본이 프로필에 없는 사실을 단정해요 (중요).** 채점관은 "본인이 제안했다면 이렇게, 아니라면 이렇게"라고 조건부 수정안을 줬는데, 수정 에이전트가 강한 쪽을 골라 본문에 "2단계로 합치자고 제안해 구현까지 맡았고"라고 단정했어요. 프로필에는 제안 여부가 없어요. 수정 내역에 "제안하지 않았다면 고치세요"라고 적긴 했지만, 본문만 복사해 내는 사용자는 놓칠 수 있어요. 예상 질문 에이전트는 이 문장을 사실로 받아 답변 구조에 "직접 제안했고"를 넣었어요. 서류 작성 단계의 "측정해 기준값을 잡았습니다" 같은 과정 서술도 같은 종류예요(이건 작성 메모에서 확인 요청을 함). 제안: 수정·작성 프롬프트에 "조건부 수정안이나 프로필에 없는 과정 서술은 단정하지 말고 [ ] 빈칸으로 남긴다"를 넣기.
2. **채점 기준에 서류로는 판단할 수 없는 항목이 섞여요.** 리서치가 만든 평가 기준이 전형 전체 기준이라 "과제 코드 품질·설계 25%"가 들어 있었고, 채점관은 지시대로 이 기준을 자소서에 그대로 써서 4/10을 줬어요. 자소서로는 보여주기 어려운 항목이 점수를 끌어내린 셈이에요. 제안: 리서치가 "서류 평가 기준"과 "면접·과제 평가 기준"을 나눠 쓰게 하거나, 채점관이 서류로 판단할 수 없는 항목은 빼고 비중을 다시 나누게 하기.
3. **채점관이 글자 수를 잘못 세요.** 채점 결과에 "본문 약 660자대, 소제목 포함 약 690자(추정)"라고 썼지만 화면 계산은 695자, 694자였어요. 모델은 한국어 글자 수를 정확히 세지 못해요. 화면에 정확한 숫자가 따로 있어서 피해는 작지만 서로 다른 숫자가 보이면 신뢰가 떨어져요. 제안: 화면이 계산한 문항별 글자 수를 참고 자료로 함께 보내기.
4. **서류 작업이 1분 40초~2분 20초 걸리고, 그중 대부분은 글이 나오기 전 "생각하는 중"이에요.** 출력의 70~80%가 생각 토큰이라 글이 화면에 나오기 시작할 때까지 1분 이상 걸리는 것으로 보여요(추정, 첫 글자 시각은 따로 재지 않음). 처음 쓰는 사람은 멈춘 줄 알 수 있어요. 제안: 대기 안내 문구("보통 1~2분 걸려요"), 또는 `effort`를 낮추는 실험(원가도 같이 줄어듦, 품질은 재 봐야 함).
5. **중지한 요청은 원가가 0으로 기록돼요.** 측정 중 17.6초 만에 끊은 서류 작성 요청이 `[usage]`에 토큰 0, `aborted: true`로 남았어요. 실제로는 그동안 쓴 토큰이 청구돼요. 사용자가 "중지"를 자주 누르면 로그 원가가 실제보다 적게 잡혀요. 제안: 스트림 이벤트(message_start, message_delta)의 usage를 받아 두었다가 끊겨도 그만큼 기록하기.
6. **한 번만 부르는 작업도 캐시 쓰기 요금(입력의 1.25배)을 내요.** 서류 작성·채점·수정·예상 질문은 같은 앞부분을 다시 보내는 일이 거의 없어서 캐시 이득이 없어요. 호출당 10~20원(원가의 2~4%) 정도라 급하지 않아요. 면접과 리서치는 캐시 덕을 크게 보니 유지해야 해요.
7. **도구 설정 오류가 "입력이 너무 길다"로 보여요.** 이번 web_fetch 400은 `friendlyError`가 BadRequest를 한 문장("입력이 너무 길거나 형식이 맞지 않을 수 있어요")으로 묶어서 원인을 알 수 없었어요. 배포 환경에서도 조직 설정에서 웹 도구가 꺼져 있으면 같은 문구가 나올 거예요. 서버 로그에는 원문이 남아요.

### 확인하지 못한 것

- web_fetch를 포함한 리서치(배포 환경에서만 가능). 공고 URL을 넣으면 페이지 읽기만큼 원가가 늘어요.
- PDF 이력서 가져오기(텍스트만 해 봄), 음성 면접, 압박·심화 난이도, 자소서 3문항 이상·1,000자 문항.
- 같은 입력으로 여러 번 돌렸을 때의 편차(작업마다 1회만 측정).
- 안전 분류기 거절과 자동 재시도(`fallbacks`) 경로는 이번에 일어나지 않았어요.
- 품질 판단은 결과 글을 직접 읽고 한 것이고, 실제 채용 담당자의 평가는 아니에요. 면접 답변이 미리 써 둔 것이라 면접 점수(56)는 지원자 실력이 아니라 "면접관이 엇나간 답에 제대로 반응하는가"를 본 것이에요.
- 동시 사용자가 많을 때의 API 속도 제한.


## 10차: 신뢰 문제 3건 수정과 모델·effort 비교 실측 (2026-11-09)

9차에서 찾은 문제 중 신뢰에 관한 1·2·3번과 원가 기록 문제(5번)를 고치고, 고친 프롬프트로 에이전트마다 모델과 effort를 바꿔 실제 API로 비교했어요. 실측 비용은 8,371원(예산 9,800원)이고, 결과 원문·스크립트·블라인드 비교 파일은 프로젝트 파일 `online-interviewer/실측/모델비교-1109/`에 있어요. 모델 조합은 아직 바꾸지 않았어요(하은 결정 대기).

### 고친 것

| 9차 문제 | 원인 | 고친 곳 |
|---|---|---|
| 1. 수정본이 프로필에 없는 사실을 단정 | 수정 프롬프트가 "개선 제안을 빠짐없이 반영"이라 조건부 수정안의 강한 쪽을 고름 | `agents.ts`에 사실 확인 규칙(`FACT_RULE`)을 만들어 작성·수정·채점 수정안·예상 질문에 붙임. 확인 안 되는 내용과 조건부 내용은 `[확인 필요: …]`로 남기고, 반영하지 않은 제안은 수정 내역에 이유를 적게 함. 면접관·예상 질문은 빈칸 든 문장을 사실로 전제하지 않음 |
| 2. 채점 기준에 과제 항목이 섞임 | 리서치가 전형 전체 기준을 표 하나로 냄 | 리서치가 "서류 평가 기준"과 "면접·과제 평가 기준"을 나눠 씀. 채점관은 서류 기준만 쓰고, 옛 리서치(표 하나)면 서류로 볼 수 없는 항목을 "서류로 판단 불가"로 빼고 비중을 다시 나눔 |
| 3. 채점관이 글자 수를 잘못 셈 | 모델은 한국어 글자 수를 정확히 세지 못함 | 화면이 센 문항별 글자 수를 `<문항별_글자수>`로 함께 보냄(`text.ts`의 `charCountText`, `client.ts`). 작성·수정·채점은 그 값만 인용 |
| 5. 중지한 요청의 원가가 0으로 기록 | 끊긴 라운드의 사용량을 버림 | `route.ts`가 `message_start`·`message_delta`의 사용량을 받아 두었다가 끊기면 더해서 기록(`partial: true`). 끊긴 라운드의 출력 토큰 일부는 여전히 빠질 수 있어요 |

화면도 바꿨어요.

- 서류 위에 "채워야 할 빈칸이 N개 있어요" 안내를 띄우고, 본문의 빈칸을 형광 표시해요. 본문만 복사하는 사용자도 놓치지 않게 하려고요.
- 문항별 글자 수 표에 빈칸 수와 "표시를 빼면 N자"를 함께 보여요. `[확인 필요: …]` 표시는 길어서, 실측 수정본 12개 중 8개가 표시만으로 700자를 넘었어요(표시를 빼면 최대 684자). 그래서 표시 때문인 초과는 빨간 "초과"가 아니라 주황 안내로 따로 보여요.
- "짧음" 기준을 제한의 80%에서 90%로 올렸어요. 작성 에이전트가 90~100%를 목표로 쓰기 때문이에요.

### 실측 방법

- 입력은 9차 실측 원문에서 뽑은 고정값(프로필, 9차 초안·채점·수정본, 면접 기록)이에요. 회사 리서치만 새 프롬프트로 한 번 다시 돌렸어요(813원, web_fetch 제외는 9차와 같음).
- 프롬프트와 참고 자료는 앱 코드를 그대로 불러 조립했고, 요청 모양(스트리밍, 캐시, effort, Opus·Sonnet의 서버 대체 모델)도 `route.ts`와 같아요. Haiku는 서버 대체 모델 기능이 없어 뺐어요.
- 서류 작성·채점·수정은 Opus high·medium·low, Sonnet high·medium, Haiku medium을 2회씩, 면접 한 턴·피드백 리포트는 Opus·Sonnet·Haiku low를 1회씩, 이력서 가져오기는 Opus low와 Haiku low로 글·PDF를 돌렸어요.
- 원가는 "첫 요청 기준"(입력 전체를 캐시 쓰기 값으로 환산)으로 비교했어요. 같은 입력을 반복해서 실제 청구액은 이보다 낮아요.
- 근거 없는 단정은 결과 글에서 9차 초안에 없던 문장을 뽑아(`newsent.cjs`) 프로필과 직접 대조해 셌어요.
